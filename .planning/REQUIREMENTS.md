# Requirements: SmokerKhata

**Defined:** 2026-11-04
**Core Value:** Zero data loss and uptime above all features — every rupee transacted must be recorded and recoverable, even on a low-end Android phone with intermittent connectivity.

## v1 Requirements

Requirements for initial release. Each maps to roadmap phases.

### Authentication & Multi-Tenancy

- [x] **AUTH-01**: Owner can sign up with a 10-digit phone number and receive an OTP via SMS
- [x] **AUTH-02**: Owner can log in with phone + OTP; session and JWT issued on success
- [x] **AUTH-03**: Owner can create multiple shops under a single account
- [x] **AUTH-04**: Owner can invite staff with roles: manager or cashier
- [x] **AUTH-05**: Cashier cannot view reports or edit past bills without explicit owner permission grant
- [x] **AUTH-06**: Every API endpoint enforces a DRF permission class tied to the user's shop role
- [x] **AUTH-07**: OTP endpoint is rate-limited (max 5 attempts per 10 minutes per phone number)
- [x] **AUTH-08**: JWT is used for API clients; session auth is used for Django admin only

### Customer Ledger (Udhaar)

- [ ] **CUST-01**: Owner/manager can add a customer with name and optional 10-digit phone number
- [ ] **CUST-02**: Staff can add a credit entry (udhaar given) with amount, note, and IST timestamp
- [ ] **CUST-03**: Staff can add a payment entry (udhaar received) with amount, note, and IST timestamp
- [ ] **CUST-04**: Customer ledger displays entries in append-only order with running balance
- [ ] **CUST-05**: Customer list is sortable by highest outstanding balance
- [ ] **CUST-06**: WhatsApp reminder link (wa.me) is generated from the customer's phone number and outstanding balance
- [ ] **CUST-07**: Aging report shows days since oldest unpaid entry per customer

### Supplier Ledger

- [ ] **SUPP-01**: Owner/manager can add a supplier with name, phone, and address
- [ ] **SUPP-02**: Staff can record a purchase bill (supplier, items, amounts, date)
- [ ] **SUPP-03**: Staff can record a payment made to a supplier
- [ ] **SUPP-04**: Supplier ledger shows purchase bills, payments, and balance due

### Item Master

- [x] **ITEM-01**: Owner/manager can create an item with category, name, selling price (paise), cost price (paise), optional barcode, GST category, and active flag
- [x] **ITEM-02**: Owner/manager can create variants of an item (e.g. Maggi masala, Maggi chicken)
- [x] **ITEM-03**: Owner/manager can mark an item inactive (soft-delete; item still appears in past bills)
- [x] **ITEM-04**: Item list is filterable by category and shows active/inactive status with label + icon

### POS Billing

- [ ] **BILL-01**: Cashier can search items by name or scan barcode from the POS screen
- [ ] **BILL-02**: POS shows a quick-add grid of frequently used items
- [ ] **BILL-03**: Cashier can add items from multiple categories in one bill
- [ ] **BILL-04**: Cashier can adjust quantity for each line item in the bill
- [ ] **BILL-05**: Bill supports four payment modes: Cash, UPI, Udhaar, Split (combination of modes)
- [ ] **BILL-06**: Bill number is unique per shop and never repeats, even when created offline (format: `{shop_prefix}-{device_id}-{local_sequence}`)
- [ ] **BILL-07**: Completed bill can be printed or shared via WhatsApp
- [ ] **BILL-08**: Offline bills are created in IndexedDB and synced when connectivity returns
- [ ] **BILL-09**: Double-sale is prevented: stock decrement and bill creation run in one atomic DB transaction with `select_for_update`

### Stock Management

- [x] **STCK-01**: Purchase entry records stock received (supplier, items, quantities, cost)
- [x] **STCK-02**: Selling an item via billing auto-decrements its stock level in the same atomic transaction
- [x] **STCK-03**: Stock changes are ledger entries — never direct column edits
- [x] **STCK-04**: Low-stock alert is shown for items below a configurable threshold
- [x] **STCK-05**: Dead-stock report lists items with no sales in N days (configurable, default 30)

### Cash Book

- [ ] **CASH-01**: Owner/manager enters opening cash at the start of each day
- [ ] **CASH-02**: Cash-in and cash-out entries are recorded with note and timestamp
- [ ] **CASH-03**: System calculates expected closing cash (opening + cash sales + cash-in − cash-out)
- [ ] **CASH-04**: Owner/manager enters actual closing cash count
- [ ] **CASH-05**: Any mismatch between expected and actual closing is flagged with the difference — never auto-corrected

### Reports

- [ ] **REPT-01**: Daily, weekly, and monthly sales and profit summary report
- [ ] **REPT-02**: Top-selling items report with quantity and revenue
- [ ] **REPT-03**: Margin per item report (selling price minus cost price)
- [ ] **REPT-04**: Reports are exportable as Excel (.xlsx) using openpyxl
- [ ] **REPT-05**: Reports are exportable as PDF using ReportLab
- [ ] **REPT-06**: Large date-range exports are generated by django-q2 background jobs, not synchronously

### Audit Log

- [ ] **AUDT-01**: Every create, update, and delete operation records the user, UTC timestamp, old value, and new value
- [ ] **AUDT-02**: All deletes are soft-only (`deleted_at` timestamp); no hard deletes from API or UI
- [ ] **AUDT-03**: Audit log entries are immutable and append-only
- [ ] **AUDT-04**: Conflict resolution (last-write-wins) losing version is preserved in the audit log

### Offline Sync Engine

- [ ] **SYNC-01**: Client generates UUIDv4 for every business record; no auto-increment IDs in the API
- [ ] **SYNC-02**: Writes go to IndexedDB (Dexie.js) first, then to a local outbox queue
- [ ] **SYNC-03**: Client pushes outbox to `POST /api/sync/push` with exponential backoff + jitter; retries on reconnect and app start
- [ ] **SYNC-04**: `POST /api/sync/push` accepts a batch of operations, each with an idempotency key; replaying the same key never creates a duplicate; each batch runs in one DB transaction
- [ ] **SYNC-05**: `GET /api/sync/pull?cursor=...` returns changes since a server-issued monotonic sequence cursor (not a timestamp)
- [ ] **SYNC-06**: Client never clears the outbox entry until the server confirms the idempotency key
- [ ] **SYNC-07**: Client shows sync status in the header: "Synced", "N pending", "Offline", "Sync error"
- [ ] **SYNC-08**: Ledger, bill, and stock entries are append-only; they are never overwritten during conflict resolution
- [ ] **SYNC-09**: Non-financial fields (item name, phone) use last-write-wins by server timestamp; losing version is kept in audit log
- [ ] **SYNC-10**: Sync tests cover: replay (idempotency), offline-to-online, conflicting edits, server restart mid-batch

### Subscriptions

- [ ] **SUBS-01**: New accounts get a 14-day free trial with all features, no payment method required
- [ ] **SUBS-02**: Plans (Monthly, Quarterly, Yearly) are stored in a Plan model editable from Django admin — no hardcoded limits
- [ ] **SUBS-03**: Plan limits include: number of employees, number of shops, backup retention days, export access
- [ ] **SUBS-04**: Owner can subscribe via Razorpay Subscriptions (web) or Google Play Billing (Android)
- [ ] **SUBS-05**: Razorpay webhook signature is verified; payload is saved to DB first, then processed by a django-q2 job; handler is idempotent
- [ ] **SUBS-06**: Google Play Billing purchase is verified on the server via the Google Play Developer API
- [ ] **SUBS-07**: Subscription status is enforced on the server on every protected API call
- [ ] **SUBS-08**: After trial/subscription expiry: 5-day grace period (all features), then read-only mode
- [ ] **SUBS-09**: Data is never deleted after expiry; Excel/PDF export is available for 90 days after expiry
- [ ] **SUBS-10**: Prorated upgrade and downgrade is supported

### PWA & Frontend

- [ ] **PWA-01**: Frontend is a React 18 + TypeScript + Vite + Tailwind CSS PWA with a service worker and web manifest
- [ ] **PWA-02**: Service worker caches the app shell so the app opens with no network (offline-first)
- [ ] **PWA-03**: IndexedDB via Dexie.js is used for offline storage
- [ ] **PWA-04**: Frontend builds to static files served by Django (whitenoise) — single deployable unit
- [ ] **PWA-05**: Three theme modes: Light, Dark, System; stored per user; switch instantly, no reload
- [ ] **PWA-06**: Design tokens follow the strict grayscale spec (no purple, no gradients, WCAG AA)
- [ ] **PWA-07**: Hindi and English UI using i18next; layouts handle longer Hindi labels with wrapping
- [ ] **PWA-08**: Touch targets are minimum 44px; POS buttons minimum 56px
- [ ] **PWA-09**: Page load under 3 seconds on 3G on a device with under 2 GB RAM
- [ ] **PWA-10**: All 10 screens implemented: Login, Home dashboard, POS/Billing, Customer ledger, Item master, Stock, Cash book, Reports, Settings, Sync status indicator

### Android (Capacitor)

- [ ] **ANDR-01**: Capacitor project wraps the PWA for Android
- [ ] **ANDR-02**: Project builds as a signed Android App Bundle (AAB) for Google Play submission
- [ ] **ANDR-03**: Google Play billing plugin integrated; purchase tokens verified on the server

### Infrastructure & Deployment

- [x] **INFR-01**: `/healthz` endpoint checks DB connectivity and returns 200 or 503
- [x] **INFR-02**: gunicorn config: worker count from `WEB_CONCURRENCY` (default 2), `max_requests` set, graceful timeout set, logs to stdout
- [x] **INFR-03**: `render.yaml` (or `Procfile`) for PaaS deploy (Render/Railway); migrations run as a release step, never on web startup
- [x] **INFR-04**: VPS fallback: `gunicorn.conf.py`, systemd unit (`Restart=always`), `nginx.conf`
- [x] **INFR-05**: `.env.example` documents every environment variable with explanation
- [x] **INFR-06**: Sentry captures all unhandled exceptions with `shop_id` and `user_id` tags; no PII in logs
- [x] **INFR-07**: `DEBUG=False` enforced in production; `ALLOWED_HOSTS` from env; `SECURE_*` headers enabled
- [x] **INFR-08**: `CONN_MAX_AGE` set; app runs within 512 MB at 2 gunicorn workers

### Backups & Restore

- [x] **BACK-01**: Nightly `pg_dump` encrypted with a key from env, uploaded to S3-compatible or Backblaze B2 storage
- [x] **BACK-02**: 30-day backup retention; backups run from a django-q2 scheduled task, not the web process
- [x] **BACK-03**: Manual JSON export per shop available from the UI
- [x] **BACK-04**: `deploy/backup.sh` and `deploy/restore.sh` scripts exist and are documented
- [x] **BACK-05**: `restore.sh` restores into a staging DB; monthly restore drill is documented

### Admin Panel

- [ ] **ADMN-01**: Customized Django admin lists shops with subscription status, MRR, churn, failed payments
- [ ] **ADMN-02**: Admin can extend a trial or plan manually with a mandatory reason note logged in the audit log
- [ ] **ADMN-03**: Feature flags per plan are configurable from Django admin

## Out of Scope

| Feature | Reason |
|---------|--------|
| Redis or Celery | Explicitly replaced by django-q2 with Postgres ORM broker; removes Redis operational dependency |
| Docker | Not in scope per spec; deployment via gunicorn/systemd or PaaS |
| WeasyPrint | Heavy system dependencies cause deploy failures; replaced by ReportLab |
| Real-time WebSocket push | Offline-first polling sync is sufficient for MVP |
| Hard deletes from API or UI | Soft-delete everywhere for audit compliance and data safety |
| Float money storage | All amounts in integer paise (BigIntegerField) — no exceptions |
| Age-restricted product compliance | Will stop and ask before adding any such regulatory category |
| WhatsApp Business API | wa.me links used instead — no API cost or approval required for MVP |
| Native iOS app | Android AAB via Capacitor is sufficient for v1; iOS deferred |

# Plan 05-01: Sync Engine Data Models & Monotonic Journal Sequence

## Goal
Implement the core data architecture for offline synchronization in a dedicated `backend/sync/` app:
- `SyncOperation`: Track processed client outbox operations by `(shop, idempotency_key)` to ensure strictly idempotent processing.
- `SyncJournalEntry`: Monotonic shop-scoped change feed sequence recording all entity state mutations (`CREATE`, `UPDATE`, `DELETE`) with integer sequence numbers and serialized payload.
- `ShopSyncSequence`: Thread-safe monotonic sequence allocator for each shop using `select_for_update`.

## Requirements Covered
- **SYNC-01**: UUIDv4 primary keys for all business entities (confirmed across apps).
- **SYNC-04**: Database models supporting idempotent operation batches.
- **SYNC-05**: Monotonic sequence cursor architecture.

## Tasks
1. Create Django app `backend/sync/` (registered in `INSTALLED_APPS`).
2. Define models:
   - `SyncOperation(id, shop, idempotency_key, entity_type, entity_id, action, status, created_at, processed_at)`
   - `SyncJournalEntry(id, shop, sequence, entity_type, entity_id, action, payload, created_at)`
   - `ShopSyncSequence(shop, current_sequence)`
3. Create service helper `SyncJournalService.record_change(shop, entity_type, entity_id, action, payload)`:
   - Atomically increments and assigns next monotonic sequence integer for the shop.
   - Saves `SyncJournalEntry`.
4. Run Django migrations and verify model constraints in pytest.

## Verification
- Unit test ensuring `record_change` generates strictly increasing sequence numbers without gaps or race conditions under concurrency.
